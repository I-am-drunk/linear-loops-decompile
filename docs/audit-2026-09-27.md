## Finding 1 — the UI theme is a FUNCTION, not a palette (the big one)

Linear's client uses StyleX. The compiled stylesheet (fetched for this audit:
`style-YZZHHG9P.css`, 565,322 bytes, now in the vault at `corpus/style/`)
declares every `--sx-*` theme variable EMPTY at `:root`. The values are computed
at runtime by `generateTheme({ base, accent, colorFormat, contrast })` in chunk
`ThemeHelper.CeMKYPhf.js`. Four parametrizations exist in
`lightThemeRefresh.DyWCsE3P.js`; the pre-React loader (`rootPreReactTheme`)
picks dark vs light by the `dark` class on `<html>`:

- **dark (default)**: `base: [5.52, 0.4, 272]`, `contrast: 27`
- **dark, high contrast**: `base: [8, 0.75, 272]`, `contrast: 90`
- **light (default)**: `base: [97.94, 0.5, 282]`, `contrast: 30`
- **light, high contrast**: `base: [98.7, 0.5, 282.86]`, `contrast: 90`
- accent (all): `[47.917542332560124, 59.30267706856808, 288.42138382943733]`
  (light themes use `[53, 52.26, 286.91]`)

(An earlier revision of this audit mislabeled the contrast-90 dark variant as
the default; corrected with the loader evidence above.)

No hex palette exists anywhere in the 1,550-chunk JS corpus (searched
exhaustively). Therefore `src/ui/src/theme.css`'s hardcoded `#08090a`,
`#5e68d0`, `#4ea7fc`, … cannot be "extracted from the corpus" as claimed — at
best sampled from the live app, at worst invented, and `#08090a`/`#e8e3e3`
already sat in R3.2's placeholder HTML, so provenance may be circular.
UNVERIFIABLE as written.

This is also the good news: exact theme parity is achievable BY CONSTRUCTION.
Reimplement `generateTheme` exactly (read the algorithm in the vault chunk
and reproduce its math in our own code — OKLCH-style ramp generation from base/accent/contrast) and
our tokens match Linear's dark, light, AND custom themes, forever, without
transcribing 453 variables. This reimplementation is a defined, testable slice:
generate both themes, sample Linear's live computed values via DevTools on
linear.app, assert equality. **That is exactly the kind of check the planned
CLI parity harness should own.**

## Finding 2 — the loops trigger model contradicts the corpus

SPECS/loops.md says `triggerType: "schedule" | "chat" | "event"` (event carries
the entity). The corpus (Issue mega-chunk enum, `fD` in `Issue.DRYymPCa.js`;
usage in `AutomationHelper.B0HEcOoo.js`) says triggerType IS the entity:

```
Issue, Project, Document, Initiative, Team, Release, Cycle, Schedule, Chat
```

(PascalCase string values.) `AutomationHelper` validates per triggerType:
`C.chat`, `C.issue`, `C.cycle`, `C.project`, `C.initiative`, `C.release`,
`C.schedule` — there is no "event" value and no separate `trigger.event` field;
triage is a condition variant, not a triggerType. Both open R4.1 PRs (#160,
#161) encode the wrong SPECS model. SPECS/loops.md is corrected in this PR.

## Finding 4 — src/ui structural gaps vs "the EXACT same UI"

Beyond tokens: the R3.4 shell invents a 4-item nav (Loops/Runs/Templates/
Settings). The user vision anchor (issue #2, 2026-09-26) is "open our page and
it feels like opening Linear" — Linear's Loops UI lives inside the Linear app
chrome (workspace sidebar with Inbox/My Issues/…, command bar, loops routes
under `/:orgKey/`). A standalone console was never ratified as the target.
React + Vite were also introduced silently, breaking the repo's
zero-runtime-dep doctrine without a decision record.

Recommendation: freeze all UI implementation. The R3.4 shell stays as a
technical placeholder or is deleted — decide after the CLI parity harness lands
and defines "same" mechanically. UI code written before that harness exists is
unverifiable by definition, which is how we got here.
